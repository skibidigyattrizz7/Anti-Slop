# Extend Anti-Slop into a senior craft guide

The library should grow by adding one short "senior" reference file per craft area, one new optional mode skill for teaching, and a written set of composition rules, while keeping every existing skill, rubric and agent as it is. The current skills already beat no-skill output: the judge preferred the skill version in **29 of 30 judged runs**, but the proof is thin and the rubrics only cover tells and basics, not senior judgement such as module design, spacing logic, structure editing, loudness targets or forking paths in analysis ([evals/RESULTS.md](../evals/RESULTS.md)). The senior layer fills that gap with sourced, checkable rules (about 900 words per area, each rule with a pass/fail check), and it reuses installed skills in three ways only: link by name with an inline fallback, borrow MIT or Apache text with credit in a root NOTICE file, or wrap (our entry skill stays the front door and calls theirs when present). The `ziad-skills` plugin has no LICENSE file and only 3 of its 45 skills declare MIT (code-review-and-quality, be-ambitious, video-lens), so the rest are link or paraphrase only. The teaching mode is a separate skill, `teach-as-you-build`, with three levels (0 just do it, 1 key choices, 2 lesson), hard length caps, a five-part decision card and one skippable question. Level 0 is the default and the result is never withheld, because the best evidence says unguarded AI help harms later skill while forced Socratic questions get ignored. Composition rules decide precedence (owner's rules, then the user's brief, then correctness, then craft, then teaching) and keep each skill working alone.

## What the library has, and what senior work still needs

The library is 12 skills and 11 agents. Its own roadmap rates it 7 of 10 on 2026-11-18, and says the weak point is proof rather than content ([ROADMAP_10.md](../docs/ROADMAP_10.md)). Since then the eval runner was built, and a held-out 3-runs-per-side test across 11 skills showed the skill average above the no-skill average in every category (for example human-code 1.00 vs 0.40, human-ui 0.86 vs 0.38) with plain-word triggers loading the right skill 80 times out of 88. Three limits matter for this plan. Writer and judge are both Claude models and no human has rated anything, so the human blind check is still owed. The code and UI must-pass checks failed in both arms in an earlier held-out run, and the code skill let a missing file crash with a raw traceback, which shows that basics are still not saturated. And the roadmap's own rule is "nothing new until steps 1 and 2 pass", which both now have, but the human check has not.

That history sets three constraints on the extension. First, additions must be small and testable: each new rule gets a pass/fail check and must show a with-versus-without difference on a held-out task, or be dropped; the agentskills evaluation guidance says assertions that pass in both arms inflate the score and should be removed ([agentskills.io](https://agentskills.io/skill-creation/evaluating-skills)). Second, the rubrics must be written before seeing outputs, to avoid the overfitting the roadmap flags; the foundations notes point at a spec-first judge and a fresh-context reviewer as the pattern. Third, the owner's standing rules win over any borrowed design guidance: the 20-item "looks vibecoded" list needs a screenshot before anything on it is added, and several installed design skills push exactly those looks (design-taste-frontend prescribes bento grids and GSAP choreography, ui-ux-pro-max suggests Lucide icons), so they are reference-only.

The structural change is minimal. Each of the eight craft skills gets `references/senior.md` (new), one new row in its "Read when" table, and added rows in its judge rubric. Nothing existing is deleted or reworded except where a senior rule contradicts it, and any such conflict goes to the owner. Because SKILL.md files must stay under 500 words and the agentskills spec asks for references one level deep ([spec](https://agentskills.io/specification)), the senior file is loaded only when the task is big, reviewed, or the user asks for senior-level work.

## Senior-level additions per area, with sources

**Code.** The biggest additions are design judgement, test judgement and reviewability. On design: prefer deep modules (a small interface hiding real behaviour), and treat pass-through wrappers and leaked decisions as red flags; Ousterhout notes that big classes can be fine when the interface is simple ([Stanford CS190 notes](https://web.stanford.edu/~ouster/cgi-bin/cs190-winter18/lecture.php?topic=modularDesign)). Use Beck's four rules as a tie-break order: passes tests, reveals intention, no duplication, fewest elements ([Fowler](https://martinfowler.com/bliki/BeckDesignRules.html)). Abstract late, because a wrong shared function costs more than a copy, and fix it by inlining back before re-extracting ([Metz](https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction)); YAGNI covers speculative features, not malleability ([Fowler](https://martinfowler.com/bliki/Yagni.html)). On tests: push each test as low in the pyramid as it can go and keep few end-to-end tests ([Vocke](https://martinfowler.com/articles/practical-test-pyramid.html)), test behaviour rather than internals, and write a failing test first for any bug fix. Google's diff-based mutation testing treats coverage as a floor and surviving mutants as missing assertions ([Google Research](https://research.google/pubs/state-of-mutation-testing-at-google/)). On reviewability: approve when a change definitely improves code health ([Google standard](https://google.github.io/eng-practices/review/reviewer/standard.html)), review design first and complexity before style ([Google](https://google.github.io/eng-practices/review/reviewer/looking-for.html)), keep changes near **100 lines and one logical change**, with refactors separate ([Google](https://google.github.io/eng-practices/review/developer/small-cls.html)), and label comments so authors know what blocks ([Conventional Comments](https://conventionalcomments.org/)). On reliability: every remote call gets a timeout sized from a high latency percentile, retries only for idempotent calls, at one layer, with capped backoff and jitter; the AWS example is that three retries at each of five layers can multiply load **243 times** on a failing dependency ([AWS Builders' Library](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter)). On security: threat-model with STRIDE per trust boundary ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/security/develop/threat-modeling-tool-threats)), validate by allowlist at every boundary ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html)), and keep secrets out of source ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)). On change in a live codebase: parallel change (expand, migrate, contract) for schemas and APIs ([Sato](https://martinfowler.com/bliki/ParallelChange.html)), feature flags classified with an owner and expiry ([Hodgson](https://martinfowler.com/articles/feature-toggles.html)), and ADRs for decisions costly to reverse ([Nygard](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)). No source was found for function-length limits, N+1 queries, caching or property-based testing, so the library must not state numbers for those as fact.

**UI.** Seniors work from a few decisions applied consistently. Body measure of 45 to 90 characters ([Butterick](https://practicaltypography.com/line-length.html)), a scale with one ratio (app UI 1.125 to 1.2, marketing 1.25 and up, per the Impeccable typeset reference), tabular figures and right-aligned numbers in columns ([Vercel guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md)). Colour built in OKLCH, with semantic tokens so dark mode is a token swap, and contrast verified by a real method rather than by lightness ([Evil Martians](https://evilmartians.com/chronicles/oklch-in-css-why-quit-rgb-hsl)); WCAG 2.2 sets 4.5:1 for text and 3:1 for UI components ([W3C](https://www.w3.org/TR/WCAG22/)), and the AA target-size minimum is **24 by 24 CSS pixels** while 44 is AAA ([W3C Understanding 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)). APCA lookups give a stricter text check but remain a WCAG 3 candidate ([APCA](https://git.apcacontrast.com/documentation/APCA_in_a_Nutshell.html)). Interaction: the three response limits of 0.1, 1 and 10 seconds decide what to show ([NN/g](https://www.nngroup.com/articles/response-times-3-important-limits/)); validate on blur, put errors beside the field, never rely on colour alone ([NN/g](https://www.nngroup.com/articles/errors-forms-design-guidelines/)); design the eight control states, with undo preferred over confirm for reversible actions. Layout: spacing by relationship (tight inside groups, at least twice as loose between), shadows from one light source and tinted to the background ([Comeau](https://www.joshwcomeau.com/css/designing-shadows/)), and the F-pattern treated as a failure mode of unformatted text to design against, not a layout to copy ([NN/g](https://www.nngroup.com/articles/f-shaped-pattern-reading-web-content/)). Motion starts with frequency: no animation for actions used a hundred times a day, otherwise transform and opacity only with reduced-motion support; the installed `emil-design-eng` and `motion-design` tables disagree on durations, so the library picks one table per project. The senior layer also adds a 30-second screen critique (squint test, job in one sentence, lightest-text contrast, one tab-through, empty and error case, 375 px check, tells scan), which is the library's own synthesis and not a sourced method.

**Writing.** The missing piece is structure before sentences. The order of passes is developmental, line, copy, proof, since each invalidates the next; the notes call this standard practice without a primary source, so it is presented as craft consensus. Concrete additions: write the point as a claim rather than a topic; do a reverse outline (one line per paragraph saying what it does) to expose five parallel paragraphs with no argument; and answer the strongest objection. Line craft comes from Gopen and Swan: keep subject and verb close, put the news in the stress position at the end, open on what the reader already has, and put action in the verb ([mirror](https://wstomv.win.tue.nl/quotes/science-of-scientific-writing.html)). The notes argue end focus is the highest-value fix for flat AI cadence, because AI sentences often end on a vague abstraction; that is an inference worth testing. Genre craft adds a Diataxis check, since mixing tutorial, how-to, reference and explanation is the commonest docs failure ([Diataxis](https://diataxis.fr/)), plus BLUF for emails and the Google rule of condition before instruction ([Google style](https://developers.google.com/style/highlights)). Editing someone else's text adds three rules: read for intent first, keep their idiom, and give at most three ranked priorities with a place and a fix.

**Chat and explanation.** The library's `human-chat` already requires a worked example before the rule. Senior additions: diagnose the reader's model with one calibrating question (the Apache-2.0 `learn` skill's core move), name the likely misconception and why it is tempting, state where an analogy breaks, give layers of depth so the reader can stop at any one, and end with a prediction task instead of a quiz. The notes found no primary study for misconception-first teaching, so the library should phrase it as practice, not as proven. Tutorial writing follows Diataxis: show the destination early, give visible results often, minimise explanation and link out ([Diataxis tutorials](https://diataxis.fr/tutorials/)).

**Fiction.** The notes found the thinnest sourcing here and the library should say so. What is confirmed: psychic distance, the felt distance between reader and events, is a controllable variable, taught by rewriting one paragraph at two distances ([Stanford](https://teachingwriting.stanford.edu/psychic-distance)). Craft consensus, not opened at source, supplies scene function (goal, opposition, change, or it is a sequel that needs a decision), want versus need, subtext, and revision in separate passes (structure, character, dialogue, distance, rhythm, cut, proof). These become pass/fail items in the fiction rubric: each scene has goal, opposition and change; distance stays consistent within a paragraph unless deliberate; at least one spoken line differs from the want. No strong third-party fiction skill is installed, so this is original work.

**Media (image, video, audio).** The notes say the audio file had no loudness numbers and the video file no grading or pacing numbers, so those are the biggest holes. Verified loudness anchors: EBU R 128 sets programme loudness at **-23 LUFS** with a true-peak ceiling of -1 dBTP ([EBU](https://tech.ebu.ch/docs/r/r128.pdf)); Spotify normalises to -14 LUFS by default and asks for true peak below -1 dBTP ([Spotify](https://support.spotify.com/us/artists/article/loudness-normalization/)). YouTube's figure was only seen in vendor blogs, so it stays unverified. Video additions are Murch's Rule of Six as a teaching heuristic with its weights flagged as illustrative, since the sources are blog summaries ([FilmDaft](https://filmdaft.com/walter-murchs-rule-of-six-the-editors-formula-for-choosing-the-right-cut/)), a shot list where every row has one purpose verb, and the grade order exposure, then contrast, then look. Image direction adds a value-before-colour thumbnail test and iterating one variable at a time; the rest is craft consensus without a fetched source. Mix order, gain staging and layering numbers are practice, unsourced, and should be marked as such.

**Games.** Design from the intended feeling backward: MDA gives eight aesthetics (sensation, fantasy, narrative, challenge, fellowship, discovery, expression, submission) and tells the designer to check each mechanic against them ([Hunicke, LeBlanc, Zubek](http://users.cs.northwestern.edu/~hunicke/MDA.pdf)). Forgiveness is invisible design, and the open-source Celeste code shows real constants: jump grace time 0.1 s (six frames at 60 fps), variable-jump time 0.2 s, 4 px corner correction ([Player.cs](https://raw.githubusercontent.com/NoelFB/Celeste/master/Source/Player/Player.cs)); the jump-buffer length was not found, so it must not be quoted. The installed `game-feel` skill (Apache-2.0) already carries layered feedback, trauma-squared shake and hit-stop numbers; the library links it. Production adds a vertical slice before multiplying content and a playtest protocol (watch hands and face, do not explain, ask what they thought they should do); the protocol is craft consensus with no opened primary source. The Three.js budget numbers are the author's own contracts, not standards, so the library cites them as starting points.

**Reports.** `real-reports` is strong on sources and recomputing, and lacks analytical rigour and structure. Additions: write the decision first and an issue tree whose branches do not overlap; fix the analysis plan before looking and report every comparison, because forking paths inflate significance ([Gelman and Loken](https://www.americanscientist.org/node/3579)); show uncertainty as shaded bands or dot-plus-range, not error bars on bars, and only when it changes the reading ([ONS](https://service-manual.ons.gov.uk/data-visualisation/guidance/showing-uncertainty-in-charts)); choose chart type by question using the FT Visual Vocabulary ([FT](https://github.com/Financial-Times/chart-doctor/blob/main/visual-vocabulary/README.md)); write takeaway titles and label directly ([Datawrapper](https://www.datawrapper.de/blog/text-in-data-visualizations)); and for spreadsheet models follow FAST rules: separate inputs, workings and checks, no hardcodes in formulas, one formula per row, a visible master check ([FAST Standard 02c](https://www.stl-training.co.uk/download/forum/40296_FAST-Standard-02c-July-2019.pdf)). The notes flag that the FAST "24 seconds to explain" rule is a house rule some dispute, so it is presented as FAST's rule. Base rates, Simpson's paradox and sampling checks are standard practice but unsourced here.

## A teaching mode that never slows the person who wants the result

**What the evidence supports.** Novices learn more from studied examples with the reasoning shown, and that benefit reverses for experienced learners, which is the expertise reversal effect ([Kalyuga et al., 2003](https://ro.uow.edu.au/edupapers/136)); support should fade as skill grows ([Renkl and Atkinson](https://link.springer.com/doi/10.1007/s11251-009-9107-8)); and retention comes from retrieval, not rereading: after two days and a week, prior testing beat restudy ([Roediger and Karpicke](https://pubmed.ncbi.nlm.nih.gov/16507066/)). All three were seen only as search summaries, not opened. The AI-specific evidence points the same way. In a field experiment with roughly 1,000 high school students, those who had a ChatGPT-like tool scored **17 percent worse** once it was removed, and a guardrailed tutor largely removed the harm ([Bastani et al., PNAS 2025](https://chibe.upenn.edu/publications/generative-ai-without-guardrails-can-harm-learning-evidence-from-high-school-mathematics)); that is a single site. In a randomised trial of 52 mostly junior engineers learning a new library, the AI group scored 50 percent on the quiz against 67 percent for hand coders, with no significant speed gain; the participants who asked for explanations alongside code scored about 68 percent, but those cells held 2 to 7 people and the authors call the pattern analysis non-causal ([Anthropic](https://www.anthropic.com/research/AI-assistance-coding-skills)). Essay writers helped by ChatGPT showed fewer metacognitive processes and no better knowledge transfer ([Fan et al.](https://arxiv.org/abs/2412.09315v1)). On the other side, a pedagogy-built tutor beat in-class active learning for 194 Harvard physics students on two topics ([Kestin et al.](https://pmc.ncbi.nlm.nih.gov/articles/PMC12179260/)), while Khanmigo's Socratic refusals led many students to quit or hunt for the answer ([Hechinger](https://hechingerreport.org/proof-points-khanmigo-math-ai-tutor/)). The design that survives all of this keeps the result, opens only a little thinking for the learner, and is opt-in. Study Mode and Claude's learning mode are both question-first ([OpenAI](https://openai.com/index/chatgpt-study-mode/), [Anthropic](https://www.anthropic.com/news/introducing-claude-for-education)); the Claude Code Explanatory style is closer to ours, since it does the task and adds short insight blocks, and Learning adds a `TODO(human)` handoff ([output styles docs](https://code.claude.com/docs/en/output-styles)). No study tested explanation length, so every cap below is a design guess to be checked with the repo's own with/without eval.

**Design.** Name: `teach-as-you-build`, a mode that other skills defer to, with SKILL.md under 500 words and the card and examples in `references/card.md`. Levels switch by plain words and stay sticky until changed. Level 0 is the default: result only, no teaching text, identical to today. Level 1 ("explain the key choices", "teach me as you go") gives the full result, then a "Why" block of at most 3 decisions at 120 words total, plus one-line code comments only where a choice is non-obvious. Level 2 ("walk me through it", "lesson") adds a first line stating what now works and the next action, up to five numbered steps of one action and one 40-word why each, a separate `lesson.md` of at most 400 words with three to five decisions in full card form and a "Try it" step, and one optional prediction or choice question at the end. From the second task in a session it explains only what is new and offers to leave the last step to the learner, which is the faded-example move. "Just do it", "I know this" or two skips drops one level; raising a level needs a request. If the user's wording is unclear the mode asks once, "New to this, or want the reasons only?", and never again.

The decision card has five parts in fixed order, one line each: decision, options considered, reason, trade-off, rule of thumb. Only decisions with a real alternative that changes the result earn a card, and a response holds at most three. This shape mirrors an ADR and puts the transferable rule last, which unaided learners tend to skip; no study tested the form itself. Per area the card carries a different check, which is what makes it senior rather than generic:

| Area | Example card line | Portable check the learner can run |
|---|---|---|
| Code | "Left two copies; a wrong shared function costs more than duplication" | Can you name the shared concept in domain words? |
| UI | "Body capped at 65ch; eyes lose the next line past about 75" | Count two alphabets across the measure |
| Writing | "Moved the number to the end of the sentence" | Read the last three words of each sentence: are they the news? |
| Reports | "Title states the finding; the reader skims titles" | Read only the titles: is the argument there? |
| Games | "6 frames of coyote time so the jump forgives" | Set it to 3 and play it |
| Media | "Mastered to -14 LUFS with -1 dBTP peaks" | Compare against a reference at matched loudness |

Hard rules apply at every level. The deliverable is complete and works, so teaching never withholds it. At most one question per response, never repeated if skipped, and it asks for a prediction or a choice rather than a definition. A term is defined once, on first use. No praise filler, no "simply", no tangents (offered after the answer). Errors get cause, fix and a one-line lesson. Teaching blocks use plain headings with no emoji or decorative badge, which keeps the owner's flagged-look list intact; this means the Explanatory style's star glyph is not copied. Output shape borrows from `i-have-adhd` (next action first, restate state such as "step 2 of 4 done", cap lists at five), though that skill's tangent suppression only partly fits and its rules after the first 4,500 characters were unread.

**Shipping and testing.** The mode ships as a skill in the plugin and as a `dist/chatgpt` copy, and optionally as a custom output style file set to level 1 for people who want it session-wide; a style is instruction, not a guarantee, per the docs. It does not go in the always-on startup hook, which should stay small; one line mapping "teach me", "explain as you go" and "I'm learning this" to the skill is enough in `hooks/chat-rules.md`. Reuse of existing skills: wrap `learn` for single-turn tutoring (Apache-2.0, add NOTICE if text is adapted), link `teach` for multi-session courses (no licence, never copy), and reuse the existing rule in `human-chat` that requires a worked example before the rule. Three evals, using the existing blind runner: level 0 adds zero teaching text; at level 1 explanations sit at the decision, are correct and number three or fewer; and a learner who reads the output answers a transfer question better than one who read the no-teaching version. The third is the one that proves the mode, and it needs human participants, since a Claude judge cannot measure learning.

## Composition rules for the extended library

The rules extend those in the foundations notes, which rest on the documented Claude Code behaviour: skill listing is budgeted at 1 percent of context with a 1,536-character cap per description, plugin dependencies work only inside one marketplace or with an allowlist, and no syntax exists for skill-to-skill calls ([skills docs](https://code.claude.com/docs/en/skills.md), [plugin dependencies](https://code.claude.com/docs/en/plugin-dependencies.md)).

First, every skill works alone. A pointer to another skill is one line in "Read when" with its fallback inline, for example "if impeccable is installed use its critique command, otherwise run rubric U1 to U6". The docs do not say what happens when a prose-referenced skill is missing, so no behaviour may depend on the pointer. Add a check to `tools/check_repo.py` that flags any named skill with no fallback line. Second, one entry skill per area and one reference per sub-task, in an Impeccable-style table with an imperative "read it". Senior files stay under about 900 words and one level deep. Third, precedence is fixed and written once in the README: the owner's standing rules first (flagged-look list, no online-system changes, secrets never in files), then the user's brief and existing project conventions, then correctness and honesty (never invent a fact, never withhold a working result), then area craft rules, then senior additions, then teaching. A borrowed design skill never overrides the flagged-look list, and when two installed skills disagree (the Emil and motion-design duration tables) the library names one.

Fourth, teaching is an overlay, never a fork. Each area keeps one rubric; the teaching mode reads the same decisions the rubric checks, so a card can only explain a rule that already exists and the library has a single source of truth. Fifth, licences gate the verb: only MIT and Apache-2.0 text is copied, with a one-line source comment in the adapted reference, "modified" marks on Apache files, and an entry in the root NOTICE; everything else is link or own words. Sixth, keep listing cost low: no new always-on router, descriptions under about 600 characters starting with "Load before starting", and rarely wanted commands such as a future `polish` set to `disable-model-invocation: true`. Seventh, subagents load their skill explicitly through `skills:` frontmatter, and `context: fork` is reserved for task-style skills, never guideline skills. Eighth, hooks inject only the short chat rules and the one-line trigger map, because additional context is capped at 10,000 characters and arrives every session. Ninth, test rather than rebuild: run skill-creator's eval loop and skill-doctor's lint over the new files, and have the rubric rows written by a fresh-context reviewer before outputs are seen.

## Conclusion

The main insight is that the library does not need more rules so much as a way to say which rules matter at which level, and the same decision cards can serve both purposes. A senior reference with pass/fail checks makes the output better; the same checks, phrased as one-line reasons with a portable test, make the explanation. That is why the teaching mode should be an overlay on the existing rubrics and not a parallel set of lessons. It also means the first thing to ship is not the teaching skill but the per-area senior files, because the cards depend on them.

Three caveats should travel with the work. The senior rules are only as good as their sources: much of fiction, media mixing, game production and report-analysis guidance is craft consensus with no opened primary source, and the library should label it that way rather than quote numbers. The teaching evidence rests on small or single-site studies, so the level caps are hypotheses until the blind runner and at least one human check support them. And the roadmap's open item still applies: until a person has blind-scored a handful of pairs and agreed with the judge, any gain from the senior layer is a Claude-judged gain, and the README should say so.
